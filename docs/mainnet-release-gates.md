# Mainnet release gates — 20 October 2026

**Status: NOT READY. Mainnet signing and financial writes remain blocked.** This document describes the current local hardening candidate and the evidence needed for a future release. It does not authorize deployment, authority migration, deposits, signing, broadcasting or reopening custody. Local source changes and mocked checks are not evidence of production deployment or host isolation.

## Scope and chain identity

The requested release includes **Solana mainnet, Base mainnet and Ethereum mainnet**. Each must pass its own acceptance evidence as well as the shared custody/accounting/host gates. A successful canary on one chain does not clear the others. Human acceptance will use explicitly approved, tightly capped mainnet canaries; offline faults and simulations precede them. Humans are not required to use testnet.

## Protections implemented in this candidate

These are bounded source protections, subject to exact-commit CI and independent review:

- Server and adapter holds refuse mainnet financial paths before deposit credit, burn consumption, backing reservation, key access or signing. Operator headers and environment authority flags do not lift those holds. The body-field middleware is an early filter only: each new financial path must resolve its stored/canonical chain and enforce the hold at the signing boundary. Adapter refusals remain authoritative if a request field is missing or renamed. Pool-derived writes and AMM/Uniswap protocol-funded writes are included.
- EVM configuration separates all four EVM identities, requires explicit HTTPS mainnet endpoints and checks fresh chain IDs at the provider transport boundary. Mainnet burns require an exact amount, explicit source-origin binding, canonical receipt block hash and finalized inclusion. Solana mainnet reads verify genesis and require finalized burn observations.
- Solana existing-mint failures cannot silently create replacement identities. SPL program ownership, initialized state, decimals, mint authority and aggregate `supply + amount` u64 capacity are checked. Mainnet EVM representation validation compares the entire runtime bytecode, including compiler metadata, with the reproducibly compiled artifact after setting every validated `_decimals` immutable reference to exactly 18. The compiler AST must contain only that immutable; malformed layouts fail closed and no wildcard masking is used. Owner, decimals and source origin are checked separately; owner-read errors cannot select a legacy raw signer.
- Mainnet managed/raw EVM signing, automatic Safe quorum signing and automatic Squads quorum signing are disabled. Key loading is lazy. Read-only mainnet status does not load local fee/quorum keys. AMM imports no longer eagerly load a fee key. Uniswap static preflight requires an explicit public caller and uses a provider, not a signer.
- Destructive operator reconciliation (`failed`, `aborted`, `free`) is refused while a safe fencing mechanism is absent. Operator deposit claims require depositor binding; operator redemptions and moves require burn/owner authorization.
- Structured authorization messages bind the app/group, exact source protocol/ticker/deployment identity, Bitcoin-mainnet vault, exact deposit or burn transaction, source representation chain/address and destination chain/address/amount. Legacy messages are rejected. Browser wallet dispatch recognizes all three explicit mainnet identities; this is offline compatibility evidence, not completion of real-browser wallet acceptance.
- Bitcoin confirmation configuration defaults to six and rejects malformed or lower values. This policy does not implement continuous canonicality monitoring or eliminate deep-reorg risk.
- Existing event-key accounting, durable ambiguous-mint reservations and historical identity holds remain applicable. Proof-of-reserves/status explicitly do not certify release readiness or complete chain reconciliation.

Offline regression suites cover the paused-worker/reconciliation race, identity substitution, overflow, read failures, wrong networks, canonical/finalized burn checks, keyless imports and mainnet write holds. This is not a complete audit, a live signer integration, a sustained platform fault rehearsal or a proof of full customer solvency.

## Implementation gates still open

### Independent proposal, approval and execution

Implement a durable workflow with separate proposer, independent approvers and bounded executor. The app may propose an intent; it must not hold, unlock or automatically invoke enough credentials to satisfy a quorum. Independent signers need different administrators, devices/organizations, recovery custody and verification paths. Separate files or wallets on the same host are one compromise domain.

Each proposal must bind a unique operation, exact network identity, exact asset/token address, recipient, integer amount, fee ceiling, expiry, replay domain and reservation version. Approvers independently verify canonical collateral/burn evidence, existing customer claims and the complete decoded transaction using a trusted display. Persist approvals and their exact signed payload. The executor can submit only the approved bytes/intent under the reservation and network constraints; changes require a new approval. Safe modules/guards, Squads permissions, timelocks and administrator powers belong in the reviewed authority manifest. Verify mint authority, freeze authority, owner and any upgrade/admin rights on every actual representation.

**Bitcoin custody is a separate mandatory gate.** Emblem must demonstrate vault-specific, least-privilege capabilities and externally enforced signer policy outside the app host. The app credential must not be able to sign arbitrary Bitcoin transactions or bypass withdrawal approval. Demand complete input ownership and source-protocol decoding, exact recipient/asset/quantity, change allowlist, absolute/rate fee limits, approved outpoints and independent approval. A representation multisig does not protect Bitcoin collateral from a compromised vault-signing credential. No raw Bitcoin key in the app is useful evidence, but does not prove custody isolation or recovery.

The recovery manifest must name public signer identities, quorum, independent recovery custodians and exact permitted recovery transactions without publishing private material. Demonstrate one signer unavailable, one signer compromised and rotated by the surviving quorum, lost quorum, provider outage and lost app database. Lost quorum must stop issuance rather than activate a single-admin bypass. Establish how Emblem vault control is recovered or revoked during a provider outage, and who can execute that path. Recover the journal and accounting evidence before authorizing any restored executor.

### Durable signing and safe reconciliation

Add an immutable signer journal outside the app's unilateral write authority. Before submission, durably record the operation, approved payload hash, exact signed transaction/hash or recoverable signing reference, EVM nonce / Solana blockhash and validity horizon / Bitcoin outpoints, authority configuration and backing claim. The accounting store and signer journal must be bound to the same deployment identity and reconciled after restore.

Use terminal tombstones and unique replay identities. The current consumed-burn primary key is globally the normalized transaction ID, even though rows also record a chain; it conservatively consumes a whole transaction across redeems/moves. Multiple burns in one transaction, or identical IDs across networks, cannot be claimed independently. This is an availability limitation, not per-log recovery support. Do not delete a reservation or free a burn because an explorer cannot find a transaction, an HTTP request timed out, a lease expired, a worker is absent from a sampled endpoint or an operator clicked “failed.” Pause and irreversibly fence every previous executor/credential generation. Prove signed work cannot later land: finalized EVM nonce cancellation/replacement as applicable; expired Solana validity with proof no durable nonce remains usable; reviewed Bitcoin conflict/confirmation and outpoint reconciliation. Prevent restored workers, replicas and queued approvals from reviving old work. Until this mechanism is reviewed and demonstrated, retain ambiguous claims and leave destructive reconciliation unavailable. This deliberately leaves stuck reservations and burned-but-unpaid claims without an automatic resolution path; track and surface that liveness liability rather than declaring it recovered.

### Full claims, quantity bounds and caps

Specify one exact base-unit accounting model for all three destinations. Customer liabilities include circulating tokens, uncertain issuance, accepted deposits awaiting mint/refund, burned-but-unpaid withdrawals, burned-but-unminted moves and attributable rounding/dust claims. Define mutually exclusive state transitions so claims are never omitted or counted twice. A burn changes the form of the customer's claim; it does not extinguish it before delivery. Reject nonredeemable source precision before burning, or implement an explicit owned dust/refund mechanism. Keep protocol inventory separate from customer entitlements.

Enforce per-transaction, per-asset, per-destination and **global across all three chains** issuance/withdrawal limits at the independent signing boundary, using exact integer source quantities. Caps must include all outstanding claims and reservations and remain effective across workers, restarts and restores. Use absolute chain-native fee/gas ceilings separately. Indicative USD prices, unreliable token-market prices and estimated portfolio values must never set financial authorization or solvency budgets. With no approved numerical manifest, all release caps are zero. Property/fault tests must cover source precision, maximum supply, uint256/u64 boundaries and migration/rounding changes.

### Continuous canonical backing and release verification

Historical `status='confirmed'` deposit rows are not continuous proof of spendable collateral. Persist canonical Bitcoin block hashes/heights and destination block hashes/slots, then continuously verify deposits, source asset validity, vault holdings, mints, burns and releases against synchronized sources. Validate indexer network, tip freshness, completeness/pagination and protocol version. Pause on lag, disagreement, missing history, reorg or unknown protocol interpretation; never substitute missing reads with zero or cached success.

Adopt and document BTC confirmation policy, Solana finality and Base/Ethereum finalized-block policy, including Base's settlement dependencies. Recheck canonicality after credit and after destination issuance. Define who funds and approves recovery if a previously accepted source deposit is removed after tokens circulate. A mempool broadcast acknowledgment is not a confirmed source-protocol release: require canonical Bitcoin inclusion **and** exact valid SRC-20/Counterparty/ACME debit/credit interpretation before declaring the customer paid. Counterparty and ACME still need independent payload/input/output/fee/signed-byte validation equivalent in intent coverage to the SRC-20 validator; separately supplied composer JSON is insufficient.

## Mainnet canary and operating envelope

Before public launch, complete offline fault/restart/concurrency tests without real signing. After the gates above pass, prepare a separate sponsor-approved canary manifest and obtain explicit transaction authorization. Mainnet-only human canaries are acceptable under these conditions:

1. One independently audited source asset initially; one sponsor with known source/destination addresses; no public deposit solicitation, unapproved participants, cross-chain moves, custom AMM or protocol-signed demo trading. Other source protocols remain excluded until individually cleared. Public user-signed AMM/router integration is a separate launch gate with wallet transaction review, slippage, deadline and approvals protections.
2. Sequential deposit → mint → burn → release on each of Solana mainnet, Base mainnet and Ethereum mainnet. The manifest specifies exact integer quantities per chain and one global quantity cap; a fresh token or vault identity requires separately reviewed deployment/migration authorization. Complete full reconciliation between canaries. Existing historical devnet tokens are excluded.
3. Enumerate every proposed transaction, recipient, authority, nonce/outpoint/validity conditions and maximum fee. One straightforward round trip needs at least four financial transactions; three destinations therefore need at least twelve, with deployment, setup, gas funding or replacement transactions separately enumerated. No blanket retry or “finish whatever is needed” signing permission. Set explicit maximum BTC miner/protocol fees, Solana fees/rent and Base/Ethereum gas in their native units. Unset amount/fee fields authorize zero spend.
4. A named on-call responder watches independent on-chain supplies, full claims, actual collateral, signer journal, queue age, RPC/indexer health, reorgs, failed releases, authority changes and budget use. Acceptance requires zero unexplained discrepancy in exact units. Alert and pause on the first discrepancy or unknown outcome; do not wait for a monetary threshold.
5. Prove a pause that blocks new proposals, approvals and execution at both app and independent signer boundaries; preserve already signed/pending work for reconciliation. Distinguish stopping intake/mint from safely satisfying existing withdrawal claims. Resume requires independent review, fresh reconciliation and restored signers/infrastructure. A web maintenance flag cannot cancel a signed transaction or stop independent token trading.

Public intake needs a separately approved asset/quantity-cap manifest, completed all-three-chain evidence, staffed incident response and demonstrated canary settlement. Current code holds stay in place until the missing architecture and external facts are reviewed; configuration changes alone cannot make this candidate release-ready.

## Appendix: external audit brief

**Objective:** assess whether compromise, concurrency, reorg, ambiguity or recovery can cause unauthorized issuance/release, omitted customer claims, permanent loss or authority takeover across Bitcoin custody and Solana/Base/Ethereum representations.

**Inputs:** exact source/build/configuration hashes; three-chain asset/authority manifest; full state machine and integer units; private sanitized accounting/signer-journal fixtures; Emblem capability/policy specification; host topology and backup route; custody/quorum recovery procedures; current findings and regression tests. Auditors receive appropriate private access through the actual operator, never shared raw credentials.

**Required adversarial cases:** app-host compromise with no quorum, malicious/stale composer, wrong RPC network, indexer divergence/reorg, forged or replayed wallet/burn binding, maximum quantities/precision/dust, concurrent workers and lease theft, pause before/after signing or submission, lost acknowledgments, delayed transaction resurrection, restores with stale workers and signers, fee/UTXO races, signer loss/replacement and complete provider outage. Test approved transaction semantics and exact runtime code, not only API responses.

**Deliverable:** reproducible findings tied to exact revisions, scope exclusions, evidence and severity; independent retest of fixes; remaining operational assumptions and explicit all-three-chain go/no-go conditions. A report or successful round trip is evidence for its tested scope, not a blanket security guarantee.
