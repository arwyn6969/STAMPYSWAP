# Receipt recovery and signer fencing boundaries

Reviewed source: `3f127550eca3895a1543dbee6c95e870ff80ee13`, with installed Emblem auth SDK **2.3.18**, Safe protocol kit **8.0.6**, and Squads SDK **2.1.4**. References below identify that source snapshot; later edits may move lines. This is source/interface evidence and an implementation design, not deployed policy, a host attestation or release clearance. Mainnet holds remain required.

SDK reference roots: Safe `node_modules/@safe-global/protocol-kit/dist/src/`; Safe types `node_modules/@safe-global/types-kit/dist/src/`; Squads `node_modules/@sqds/multisig/lib/`; Emblem `node_modules/@emblemvault/auth-sdk/dist/`. Installed interfaces are evidence of the available client surface, not proof of a remote service's enforcement.

## What is missing from the existing journal

`migrations/001_custody_accounting.sql:9–12` stores an operation key, action, canonical asset ID, amount, chain, recipient, state, transaction ID, result JSON and timestamps. It does not persist the exact representation address, signed authorization/payload hash, authority configuration, execution generation, fee bounds or chain nonce/validity evidence before signing. The unique operation key protects app-side allocation, not every possible signer invocation.

`server.js:1393–1404` writes the transaction ID during completion. Mint accounting and the mint ledger's `dest_tx` are written after external execution (`server.js:1268–1283`). Solana signs, broadcasts and waits before returning the signature (`sol-mint.js:151–164`); EVM calls `mint().wait()` before returning (`evm-mint.js:98–102`). Safe executes before returning its outer hash (`safe.js:107–116`); Squads creates/approves/executes before returning (`squads.js:176–201`). A crash or lost response can therefore lose the exact signed-work identity even while its reservation survives.

Redemption's pending ledger insert does not store the requested Bitcoin recipient or signed preimage; `consumed_burns` stores owner/amount but not that recipient or the signed consent (`server.js:2157–2167`; migration lines 16–19). Bitcoin adapters return success after a broadcast acknowledgment (`custody.js:87–93`, `166–172`, `191–198`), and the server immediately finalizes (`server.js:2214–2215`). That is not proof of confirmed, protocol-valid delivery. A burned-but-unpaid claim must survive until delivery evidence establishes otherwise.

Positive manual completion is not receipt verification: supplied transaction strings currently reach mint accounting, stamp completion and redemption finalization without independent receipt validation (`server.js:2317`, `2339–2345`, `2369`). Missing RPC history, a timeout, lease expiry or an absent worker must never authorize freeing a reservation or burn identity.

## Implementable recovery pipeline

Separate **observation**, **acceptance** and **execution**:

1. Before requesting any signature, persist an immutable execution intent: deployment/group, user-authorization hash, unique source claim, exact asset/network/representation, source/destination integer quantities and decimals, recipient, authority/policy hashes, fee ceilings and reservation generation. The current wallet-authorization v1 remains user consent; an execution intent additionally binds signer and fee policy.
2. A separately controlled signer journal records each approved attempt before broadcasting: exact transaction/message hash and recoverable signed bytes/reference, plus the authority-specific execution identity below. The app receives a durable reference, not permission to sign arbitrary payloads. Retrying an attempt may rebroadcast only identical approved bytes; rebuilding a transaction needs an explicitly linked attempt, never a second untracked effect.
3. A read-only observer verifies receipts against that recorded intent. EVM: exact chain/runtime/origin, canonical finalized block, token address, mint/release event and exact recipient/amount, with Safe execution identity where applicable. Solana: genesis, finalized successful transaction, exact canonical program/mint/recipient/base units and complete approved instruction/message identity. Bitcoin: exact signed transaction/outpoints, canonical inclusion and confirmation policy, independently decoded valid SRC-20/Counterparty/ACME debit and recipient credit. Broadcast acceptance and transaction success alone are insufficient.
4. Store an immutable effect identifier `(network, transaction, log/instruction index)` and bind it to one intent. Reject reuse, conflicting evidence and multiple interpretations. If the supported DB API cannot atomically bind receipt consumption and accounting, use an idempotent append-only acceptance event with durable readback and an external unique receipt registry; do not invent a multi-request transaction guarantee. Historical effects need reconciliation before this registry can authorize old claims.
5. Only accepted evidence can drive a positive once-only accounting transition. Unknown/reverted/missing observations retain the original customer claim. Keep delivery, accounting materialization and signer-attempt retirement as distinct states. An observer can report a match now; it cannot turn an arbitrary caller's receipt assertions into authority.

The narrow local recovery repair available immediately is to require the existing exact source-debit event, successful rematerialization and readback before advancing a pending move. `test/positive-reconcile.test.cjs` covers missing debit, failed materialization and successful repair. It performs no new chain effect and does not require freeing any reservation.

## Authority-specific retirement

**Safe:** installed `Safe.d.ts:167–188` exposes transaction construction, `createRejectionTransaction(nonce)` and Safe transaction hashing; `Safe.d.ts:93` exposes the Safe nonce. `types-kit/dist/src/types.d.ts:23–38` binds the Safe payload to its own nonce, with no built-in expiry field in that type. Record Safe address, chain, Safe nonce, Safe transaction hash, exact calldata/operation and approved configuration. A finalized governed rejection/other verified execution must consume the **Safe nonce**; replacing the executor EOA transaction does not revoke the still-executable Safe approvals. Determine which payload actually executed before assigning financial consequences. Guards/modules/alternate execution paths require explicit review. Expiry requires an actually enforced guard/policy; a UI timestamp is insufficient.

**Squads:** `generated/accounts/VaultTransaction.d.ts:17–25` persists multisig/index/message. `generated/types/VaultTransactionMessage.d.ts:11–18` contains accounts/instructions/lookups, **no recent blockhash**. Proposal status includes Approved, Executed and Cancelled (`generated/types/ProposalStatus.d.ts:17–36`); execution identifies multisig plus transaction index (`rpc/vaultTransactionExecute.d.ts:6–15`). Expiry of one outer Solana execution transaction does not retire the durable approved proposal. Require finalized governed cancellation/invalidation supported by the exact deployed program, verify proposal/transaction identity and all execution paths, and retain an external tombstone preventing a fresh proposal for the same intent. `proposalCancel[V2]` exists in the installed interface, but its comments describe config transactions; that interface alone does not establish a vault-proposal cancellation guarantee. Review/test deployed program semantics before claiming retirement.

**Direct Solana/EVM and Bitcoin:** record every signed attempt. For a direct Solana transaction, prove validity expiry and absence of reusable durable-nonce authority; for EVM, establish which finalized transaction consumed each recorded signer nonce. Neither implies that the intended effect failed. A signed Bitcoin transaction has no general application TTL: prove a reviewed canonical conflicting spend/retirement for every usable attempt/outpoint and retain the claim until its actual outcome is reconciled. Deep reorg or provider disagreement reopens uncertainty and must halt effects.

## External custody and monitoring boundary

The installed Emblem `SignerConfig` exposes authentication/base URL (`dist/types/signers.d.ts:9–25`); signer interfaces expose direct transaction signing/broadcast and PSBT signing (`signers/ethers.d.ts:2–17`, `solana.d.ts:12–28`, `bitcoin.d.ts:33–47,79–85`). These checked interfaces do not establish an operation-key, immutable journal, approval or stale-generation enforcement contract. This does not prove the vendor lacks such features; obtain the actual enforced server policy/API. Sending a custom header or wrapping the SDK locally is not proof.

Move unrestricted Emblem signing capability and quorum keys off the app host. The app may propose; independent approvers verify source evidence and decoded transactions; a bounded executor submits approved work. The external policy must enforce global claims/caps, one execution identity per intent, generations, allowed vaults/operations, fees and emergency stops. A stale app process must be unable to obtain new authority or mutate that journal.

A separate read-only monitor can be implemented now around stored canonical hashes/heights/slots and receipt observations. It must check freshness/completeness, re-read previously accepted source deposits and destination effects, detect divergence and produce a latched halt/evidence record. Its halt must ultimately be enforced by the independent signer policy. An app-local flag or healthy snapshot cannot protect funds after app-host compromise. Actual off-host deployment, vendor capability restrictions, recovery custody and host isolation remain external gates.
