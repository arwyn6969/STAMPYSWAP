# StampySwap security audit

**Target:** `github.com/arwyn6969/STAMPYSWAP`  
**HEAD:** `2345961119c001d8cd286ab0ca6a108258d7c200`  
**Date:** 2026-09-21  
**Scope:** source at this commit (server, custody, mint/AMM/Uniswap modules, contracts, frontend). Not a formal third-party audit. No production secrets were present in the tree.

## Executive summary

StampySwap is a **custodial wrap + DEX** for Bitcoin-native assets (SRC-20, Counterparty, ACME) into EVM/Solana representations. At this HEAD the repo is already on a **Base mainnet track**: real Emblem-managed Bitcoin custody, real ACME/XCP redeem paths, and a live Uniswap V2 TREES/ACME market. That is a different risk class from the “Phase 0 discovery / testnet demo” comments still scattered through the code.

The architecture has several mature defenses (per-asset locks, txid idempotency, BIP-322 deposit binding, solvency checks, operator gates on direct mint / pool create, `.gitignore` for key material). It also has **public endpoints that can move or desync real value** if `STAMPY_CUSTODY_LIVE=1` or unused collateral exists.

This PR hardens the worst of those surfaces. Residual issues below still need an explicit go-ahead before treating the protocol as mainnet-safe.

## What is in good shape

- No secret files in git (`git ls-files` clean against keypair/deployer/owners/custody-live/operator-token/authority/.env).
- Request bodies capped at 64kb; write endpoints have process-local rate limits and a 120/hr global gas ceiling.
- Deposit mint binds the Bitcoin **source** with BIP-322 and matches it to the on-chain sender (SRC-20 + ACME).
- ACME + Counterparty redeem assert compose `asset` / `destination` / `quantity` before the vault signs.
- Per-asset `withAssetLock` closes the obvious check-then-mint race.
- Ledger keys (`acme:<txid>`, SRC-20 txid, stamp-bridge burn txid) are unique-index style idempotency.
- Stamp-bridge releases only to the on-chain burn source and requires extra confirmations.
- Frontend generally `esc()`s values before `innerHTML`.
- Mainnet token (`StampyRepMainnet.sol`) is OZ ERC-20 + Ownable; testnet token is a hand-rolled minimal ERC-20.

## Findings

Severity: **P0** exploitable value / insolvency · **P1** likely value or integrity under live flags · **P2** defense-in-depth · **P3** hygiene / correctness.

### P0 — `/api/custody/redeem` released vault assets without proving a burn (fixed in this PR)

Comment says burn-then-release. Code released first and only decremented the **database** circulating figure. Anyone who could hit the endpoint while `custody.isLive()` was true could drain the Emblem vault up to “circulating”, without holding or burning reps.

**Fix:** public callers must pass `burn_txid`; server verifies an on-chain Transfer→0x0 / SPL burn of the rep, rejects replayed burn txids, then releases. Operator header remains a back-office override.

### P0 — `/api/redeem` was a public accounting-only burn (fixed in this PR)

No on-chain burn, no vault release. A public POST reduced `representations.circulating_supply` and inserted `direction='redeem'` rows. That:

- bricks honest `/api/custody/redeem` (circulating too low),
- inflates `redeemedBase` and lies in proof-of-reserves,
- does not by itself mint free tokens (collateral slack stays constant) but desynchronizes the only solvency oracle the protocol has.

**Fix:** disabled unless `STAMPY_PREVIEW=1` or operator token is present. Real path is custody redeem.

### P0 — `/api/amm/swap` minted protocol-backed reps for any caller (fixed in this PR)

The handler `performMint`s the input token into the LP, then swaps. Output is forced to the vault (so it is not a free drain of the *other* side), but it is still:

- unauthenticated minting against unused collateral,
- a gas drain on the protocol signer,
- a way to shove the pool price around with protocol inventory.

**Fix:** `requireOperator`. User swaps on mainnet are the Uniswap deep-link already in the UI.

### P1 — `getAssetByTick` collision on deposit mint (fixed in this PR)

`/api/custody/verify-deposit` used bare-ticker lookup. Dispatch order is SRC-20 → XCP → ACME. `ACME` / `SOAP` exist on multiple protocols. A user depositing the ACME-protocol asset could be credited as SRC-20 (or rejected), and the wrong whitelist/decimals/ledger path would run.

**Fix:** `resolveAsset()` so `acme:ACME` / `protocol` qualifiers win. Callers must send the qualified ticker for collided names.

### P1 — Counterparty deposit attribution is not per-tx

XCP “enhanced sends” hide the destination in OP_RETURN. Credit is **vault balance minus already-credited**. `sentToVault(source)` only proves the signer *ever* sent that asset to the vault. After one real deposit, any other past sender of the same asset can BIP-322-bind and claim leftover uncredited balance.

Mitigations in code (in-flight redeem gate, availBase cap) stop infinite mint, not theft of a co-depositor’s unclaimed delta.

**Recommendation:** stop minting XCP against balance-delta. Require a compose/decoder + txid, or a memo/OP_RETURN binding, before more XCP assets are whitelisted.

### P1 — SRC-20 redeem signed stampchain’s PSBT with weak param asserts (partially fixed)

Unlike XCP/ACME, the SRC-20 path did not check that the returned PSBT matched tick / amount / destination / vault source. A compromised or confused stampchain compose could have the vault sign an arbitrary transfer of vault holdings.

**Fix:** assert echoed fields when present. Residual: stampchain may not echo those fields; there is still no PSBT decode of the actual SRC-20 JSON / outputs. Next step is decode-and-compare the inscription payload before `signPsbt`.

### P1 — Release-then-record crash window remains

Custody redeem and stamp-bridge still broadcast, then write the ledger. A crash after broadcast and before `INSERT` allows a retry to release again (stamp-bridge is protected only if the first insert landed).

**Recommendation:** write a `pending` row with a unique burn/request key *before* broadcast; transition to `released` after txid; refuse a second broadcast while `pending` is young.

### P1 — ACME finality default is 1 confirmation

`ACME_CONFIRMATIONS` defaults to 1. CORTEX reorgs undo ops. Mainnet wraps should default to ≥3, matching `STAMP_BRIDGE_CONFIRMS`.

### P1 — Custom testnet AMM / ERC-20 are not production contracts

`StampyPair` (gen-amm.js) and the hand-rolled `StampyRep` (gen-erc20.js):

- no reentrancy guard (ERC-20 callbacks during `swap` / `addLiquidity`),
- reserve updates use `uint112(...)` truncation,
- no `removeLiquidity`,
- mint has no cap; solvency is **off-chain only**,
- no permit / hooks / pause.

Mainnet reps should stay on `StampyRepMainnet.sol` (OZ). Do not deploy `StampyPair` to Base mainnet; Uniswap V2 is the right call.

### P1 — Uniswap vault swap used `minOut = 0` (fixed in this PR)

`uniswap.js` `swap()` previously passed `amountOutMin = 0` (sandwich / partial fill). Now quotes `getAmountsOut` and applies 50 bps slippage. `addLiquidity` still uses `amountAMin/amountBMin = 0` — operators seeding pools should pass floors.

### P2 — Operator token compared with `===`

Switched to `crypto.timingSafeEqual`. Token-in-header is still a single shared secret; prefer session auth + allowlist.

### P2 — `/api/move` burn verifier is shallow

- No confirmation depth / finalized block.
- Any burn ≥ requested amount counts (a large burn can back a smaller move; leftover is not tracked for a second move of the same txid because `btc_txid` is the full burn tx — good).
- Does not bind the burner to `to_address` (anyone who sees a burn can mint the dest-chain rep to themselves). Same class of bug deposit-binding already fixed.

**Recommendation:** require the burn source / `from` to match a signed receive binding, and require N confirmations.

### P2 — `mintCritical` labeled every EVM mint as testnet and every origin as `src-20` (fixed)

`base-mainnet` now reports `mainnet`. `srcOrigin` uses `asset.source_protocol`.

### P2 — Keys created on first import

`evm-signer.js` / `sol-mint.js` / `squads.js` / `safe.js` generate and write key material if the file is missing. Fine on a locked artifact host; dangerous if this tree is ever started on a laptop or in CI. Prefer fail-closed unless `ALLOW_KEYGEN=1`.

### P2 — Rate limit is not per-client

Comment is honest: all traffic is assumed to arrive via the dashboard proxy. If the Node port is reachable directly, one IP shares the global 120 gas-ops/hour with everyone — or a burst of 20 mints/minute until the ceiling.

### P2 — No HTTP security middleware

No Helmet, no explicit CORS policy, `app.listen` on default interface. Relies on the dashboard reverse proxy. Document that the process must not be internet-facing.

### P2 — `/api/wrap/route` still advertises `preview: true` and “reps are testnet”

Mainnet TREES/ACME pool is live. External terminals will show the wrong trust model.

### P2 — Trust endpoint still says “roadmap_to_mainnet: security audit, custody provisioning”

Custody and a mainnet market already exist. Stale honesty is a disclosure bug.

### P3 — `soljson.js` (~9 MB compiler blob) is committed

Supply-chain surface and repo bloat. Pin a hash and fetch at build time, or vendor via npm `solc`.

### P3 — Public vault address + balances

`/api/custody/status`, `/api/wrap/route`, `/api/trust` publish the live vault. Expected for a peg; attackers will watch it. Keep solicitation copy accurate.

### P3 — `parseFloat` on token balances in AMM create/swap external path

Use BigInt/base units. Fine for testnet mocks; wrong for mainnet externals.

### P3 — Wallet sessions stored even when verification fails

Low risk; can fill the DB. Auth itself is nonce + signature.

## Threat model notes (not code bugs)

- **Emblem API key is the vault.** Compromise of `EMBLEM_API_KEY` or the artifact host = mint authority + BTC spend. Multisig migration (Squads/Safe) is built but not the default.
- **Off-chain solvency.** Nothing on Base stops the owner from minting uncapped. PoR is a SQL view plus indexer reads.
- **ACME envelope v1→v2 rewrite** is empirical. If ACME changes headers or the 888-sat fee output, redeem breaks or burns fees. Keep env overrides and a live canary.
- **Indexer trust.** SRC-20 (stampchain), XCP, ACME.pics, mempool.space. A lying indexer can delay or (for balance-delta XCP) distort credits.

## Residual before calling mainnet “done”

1. Per-tx XCP attribution or freeze XCP mint.
2. Decode SRC-20 PSBTs before sign.
3. Burn-binding on `/api/move` + confirmation depth.
4. Pending-row before any vault broadcast.
5. Raise ACME confirmations.
6. Do not internet-expose `server.js`; keep operator token + Emblem key off the app host if possible.
7. Independent review of `redeemAcme` tx construction (fee output, envelope rewrite, change).
8. Refresh `/api/trust` and `/api/wrap/route` copy so mainnet is not described as preview/testnet.
